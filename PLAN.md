# EVCC

The intent of this project is to have an open source implementation of an EVCC using HLC via the standards `ISO 15118-2`, `ISO 15118-20`, `IEC 61851-23` and `DIN Spec 70121`.

Unlike JosEV, it will be portable enough to deploy on resource constrained, realtime, systems (so it can work with nostd). It can also be used as a test platform for EVSE software.

## Scope

Milestone 1 targets **ISO 15118-20**, since it dictates the abstraction for the EV side.

- DC charging, no BPT, Dynamic control mode.
- Authorization: **EIM only**. PnC is a later milestone, added behind the `Ev` trait (certificate and signing hooks).
- Transport: both plain TCP and TLS.
- SLAC comes later. It is tested on Linux, using `unshare` network namespaces to separate the EV from the EVSE simulation.
- Later milestones (BPT, AC in -20, -20 PnC extras) are evaluated when we get there. PnC, DIN SPEC 70121 (DC) and ISO 15118-2 (DC, AC, PnC) are done, see the entries at the end.

## Architecture

### Sans-IO core

The core is a pure `no_std` state machine. It is driven by events (received bytes, timer expiry, EV input) and emits actions (bytes to send, arm/cancel timer, EV requests). Because it asks the host to arm timers, it never needs to be polled. Host adapters supply the real I/O.

- **V2GTP framing and SDP live in the core.** SDP is a separate small sans-IO machine from the session machine. The host runs SDP, gets the result (address, port, secure or not), opens the connection, then starts the session machine.
- **TLS lives outside the core**, in the host adapter (the `openssl` crate on Linux, something else on embedded). The core only sees a byte stream and a "secured" flag.

### EV side: hybrid

- An `Ev` trait for static and instant facts (EVCCID, battery limits, supported services), so simulated and real EVs are easy to swap.
- Events and actions for anything physical or slow (cable check, precharge, contactors, dynamic-mode targets, stop intent).

The exact trait contents are settled slice by slice.

### Memory: no-alloc, arena-based

- The core and codec are `no_std` with no `alloc`. An optional `alloc` feature only adds convenience helpers.
- The worst-case message is large; keeping it inline overflows the stack. So:
  - **Transient messages** are decoded into and encoded from a bump arena. They borrow from it (`<'a>` lifetimes) and are only valid for one step. The arena is reset between messages.
  - **Persistent session state** (negotiated parameters, selected service, schedule) uses small inline fixed-size types. Anything needed across steps is copied out of the message.
- **The host provides the memory.** Separate RX, TX and arena buffers are passed in as `&mut [u8]`, so the host decides placement and sizes (static, heap, or a specific RAM region).
- Running out of arena or buffer space is a defined error (`ArenaFull`, `BufferTooSmall`, `CapacityExceeded`), never a panic or silent truncation.

### Logging

- The core has no logging dependency. It emits **typed log records** through a sink trait (message RX/TX, state changes, timers, response codes, decode errors).
- Adapters render them: `log`/`tracing` on Linux, `defmt` or a ring buffer on embedded, or nothing. Tests can assert on the records directly.
- Levels by meaning: per-session milestones and non-OK response codes at `info`; per-message events and timers at `debug`; raw payload hex and decoded contents at `trace`.
- The `DC_ChargeLoop` repeats for the whole session, so at `debug` and above only changes are logged (a target changed, a limit hit, a non-OK code). Full loop contents are `trace`.
- Errors carry context: message kind, state, and field or response code.
- A Cargo feature can strip `trace` at compile time.

## Codec generation

ISO 15118-20 messages are schema-informed EXI. A generator tool (`exi-gen`) reads the XSDs and emits `no_std`, no-alloc, arena-based Rust.

- The XSDs are freely downloadable but ISO-copyrighted, so they are **gitignored** and fetched by a download script.
- The generated code is also **gitignored** (it is a transcription of the schema). A fresh clone runs `cargo xtask setup` to download the XSDs and generate the codecs.
- The generator must be **fast**: hash-cached and incremental, skipping work when the XSDs have not changed.
- Where the XSD declares `maxOccurs` / `maxLength` they are used as validation limits. Where it is unbounded, the limit is a named constant, recorded as a decision rather than guessed.

### Verifying the codec

A generator that only round-trips its own output can be consistently wrong, so:

1. **Independent reference vectors** are the correctness oracle: `(XML, EXI bytes)` pairs from an independent EXI implementation (e.g. EXIficient) run against the same XSDs and options. Our codec must match byte-for-byte in both directions. The generation script lives in `xtask` (needs Java, optional, cached). The vectors are gitignored like the XSDs.
2. Round-trip and property tests as an ongoing safety net.
3. Fuzzing the decoder, so a hostile EVSE can never cause a panic or overrun the arena.
4. Captured traffic and interop against an external EVSE stack, later, in the Linux harness.

## Decided during implementation

- **EXI options** (verified against EXIficient 1.0.7): schema-informed, bit-packed, default (non-strict) fidelity, no options in the header, so streams start `80 00`. Strict mode produces different streams (`80 07`) and is not what real stacks use.
- **Schema source:** `https://standards.iso.org/iso/15118/-20/ed-1/en/` (same as cbExiGen's auto-download).
- **Reference vectors:** `crates/xtask/java/EncodeVector.java` plus the EXIficient jars (downloaded into the gitignored `data/vectors/lib`). Inputs live in `xtask/vectors/*.xml`. Needs a JDK; on this Mac Homebrew's `openjdk` is at `/opt/homebrew/opt/openjdk/bin`.
- The AppProtocol XSD has no `elementFormDefault="qualified"`, so its child elements are in no namespace; only the root carries `urn:iso:15118:2:2010:AppProtocol`.
- **Event codes** (default fidelity, verified): a state with one production plus the escape takes 1 bit; the document root and repeat states take 2; every typed value has a 1-bit CH before it and a 1-bit EE after. Finite `maxOccurs` is **unrolled** (after the 20th `AppProtocol` only EE remains, coded in 1 bit). The generator must reproduce this.
- **String table:** a repeated string value is a hit (`uint 0`, then ⌈log2(table size)⌉ bits); the table grows only on misses. Needed in both directions.
- **Strings** are a length+2 unsigned int followed by one unsigned int per code point; `unsignedInt` is an EXI unsigned int, `unsignedByte` 8 bits, a bounded int is offset-from-minimum in ⌈log2(range)⌉ bits, enums are ⌈log2(n)⌉ bits.
- **Root event code** (verified): the document grammar holds every global element of the schema *and its imports* (CommonMessages 28 + CommonTypes 2 + xmldsig 24 = 54), sorted by local name across namespaces, plus `SE(*)`. The root code is the index in that list, in ⌈log2(N+1)⌉ bits (6 for `common`: `SessionSetupReq` = 35, `Res` = 36). `xtask/java/DumpRoots.java` and `DumpGrammar.java` print EXIficient's view for cross-checking.
- **Enumerations** are the declaration-order index in ⌈log2(n)⌉ bits (`responseCodeType`: 40 values, 6 bits). `xs:unsignedLong` is an EXI unsigned int (up to 10 octets); `xs:hexBinary` is a length uint plus raw bytes.
- **Empty string elements** (resolved 2026-10-16): an empty element has no characters event in the XML infoset, so EXIficient writes the second-level `EE` of the element's first state: first-level code 1 (the escape; CH is 0), then a 3-bit second-level code of value 0, and no further `EE`. Probed with `SessionStopReq` where an empty `EVTerminationCode` precedes `EVTerminationExplanation` (the following bits fix the width), checked in all four positions. `Enc::string_element` writes it, `Dec::string_element` reads it and also accepts the other legal form, `CH` with a zero-length value. An empty value is never in the string table and is not added to it.
- **`xs:integer`** is of any size (EXI: sign bit, then the unsigned integer of the magnitude, minus one when negative): `exi::Integer` keeps a big-endian magnitude (arena-allocated on decode, no size limit; the use is the X.509 serial number, at most 20 octets by RFC 5280). The xmldsig type `X509IssuerSerialType` (`RootCertificateID` in `ListOfRootCertificateIDs`) is modelled (`XMLDSIG_MODELLED` in `exi-gen`, module `xmldsig`); verified against EXIficient with serials from 0 to 40 octets, positive and negative. Attributes of these schemas are namespace-qualified (`cm:Id`), which an XML input for EXIficient has to respect or it silently falls back to untyped values.
- **V2GTP / SDP constants** (checked against ISO 15118-20:2022): header `01 FE` (Tables 12/13), 16-bit payload type (Table 14), 32-bit length. SDP uses multicast `FF02::1`, UDP port 15118; request payload = security (`00` TLS, `10` none) + transport (`00` TCP) (Table 21, V2G20-141/623); response = 16-byte address, 16-bit port, security, transport (V2G20-153). EVCC timing: wait at least 250 ms (V2G20-159), then repeat (V2G20-160), at most 50 requests (V2G20-161), then a timeout (V2G20-162). -20 only runs over TCP+TLS (V2G20-1804/1805); plain TCP here is a test mode.
- **-20 payload types** double as grammar selectors: `0x8001` SAP (AppProtocol schema), `0x8002` mainstream (CommonMessages), `0x8003` AC, `0x8004` DC, `0x8005` ACDP, `0x8006` WPT. The session machine picks the codec module from the payload type.
- **Crate layout change:** V2GTP framing and the SDP message types live in a small shared `v2gtp` crate (the EVSE simulator needs them too); only the SDP *client machine* is in `evcc-core`.
- **Session machine shape** (`evcc-core::session`): host reads from the socket straight into `Session::rx_space()` (host-provided RX buffer) and reports `Event::Received(n)`; V2GTP reassembly happens in the core. Each call returns a `Step { send, timer, notice, end }`; `send` is a fully framed message in the host-provided TX buffer. Decoded messages live in the per-frame arena; only small fixed state (session id) persists. Typed `log::Record`s go to a `LogSink` and may borrow from the message.
- **Timeouts** (Table 215): `V2G_EVCC_Msg_Timeout` is 2 s for every request except `ServiceDetailReq` and `CertificateInstallationReq` (5 s); `V2G_EVCC_Ongoing_Timeout` 60 s (responses with `EVSEProcessing` Ongoing); `V2G_EVCC_Sequence_Performance_Time` 40 s; `V2G_SECC_Sequence_Timeout` 60 s (0.5 s for the charge loop responses, to be handled with the loop). The EVCC repeats a request while Ongoing within the sequence performance time (V2G20-1582).
- **`Ev` trait so far**: `evcc_id()`, `now_micros()`, `dc_connector()`, `dc_limits()`, `schedule_request()`.

## References to the standard

Where code implements a specific, citable behaviour (timers, mandated message handling, tables), its doc comment carries `Ref: ISO 15118-20:2022 <V2G20-NNNN | Table N | clause>`. Rules:

- The standard text is in `standards/` (gitignored). Only cite what you have checked there; if a requirement id cannot be found the comment says `TODO, not yet identified`.
- Checked so far: Table 14 (payload types), Table 21 (SDP encoding), V2G20-159..162 (SDP timing), V2G20-1804/1805, Table 204 + V2G20-1355 (service ids), Table 207 (DC service parameters), Table 215 (timeouts), V2G20-1582 (repeat AuthorizationReq), V2G20-1534..1538 (header TimeStamp), V2G20-2103/2104 (DepartureTime), Annex A response code matrix.
- The header `TimeStamp` is microseconds in EVSE time and increasing (V2G20-1534, 1537); `Session` derives it from `Ev::now_micros` and the offset learned from `SessionSetupRes` (V2G20-1535, 1536, 1538).

- **Timers**: `Timer::{Sdp, Response, Ongoing}`; a step carries up to two `TimerCmd`s (`Arm{timer, ms}` / `Cancel(timer)`); the host reports expiry as `TimerExpired(timer)`. The `Ongoing` timer bounds a repeated `Ongoing` exchange (60 s, `V2G_EVCC_Ongoing_Timeout`, Table 215) and is armed once, on the first `Ongoing` response.
- **Authorization grammar facts** (verified with EXIficient): `AuthorizationServices` (`maxOccurs=2`) is unrolled (2-bit state after the first entry, 1-bit after the second); `xs:boolean` is 1 bit; the EIM/PnC choice is 2 bits and EIM is an empty element followed by an EE. The choice width is unobservable in the EIM vectors (padding); a PnC vector will confirm it.
- **`Ongoing_WaitingForCustomerInteraction`** does not appear in the 2022 text (only in the schema, presumably from the amendment; `standards/ISO 15118-20 DAM 1.pdf`); it is treated like `Ongoing`. Check the amendment.
- **Services grammar facts** (verified with EXIficient, see `crates/codec/iso15118-20/src/services.rs`): the CommonMessages root codes continue at ServiceDetailReq=29, Res=30, ServiceDiscoveryReq=31, Res=32, ServiceSelectionReq=33, Res=34; attributes are namespace-qualified in these schemas (`attributeFormDefault="qualified"`), so `Name` carries the `cm` namespace and `Exponent`/`Value` the `ct` one; `Parameter` has a 1-bit `AT(Name)` code and a 3-bit choice code (bool=0, byte=1, short=2, int=3, rational=4, finiteString=5); `xs:byte` is an 8-bit offset, `xs:short`/`xs:int` are EXI integers (sign bit, then magnitude, minus one when negative); `maxOccurs` lists are unrolled (1-bit first SE, 2-bit repeat/end state, 1-bit end after the maximum, verified at 8 and 16).
- **String table**: literals enter the global partition and the local partition of their qname (here `Name` and `finiteString`); hits (local `uint 0` + index, global `uint 1` + index) change nothing. Index widths are ceil(log2(partition size)). The decoder counts first, then builds, so storage is exact; table capacity is 64 distinct strings per message.
- **DC service parameters** (Table 207, checked): `Connector` 1 Core, 2 Extended, 3 Dual2, 4 Dual4 (matched via `Ev::dc_connector`); `ControlMode` 1 Scheduled, 2 Dynamic; `MobilityNeedsMode` 1 EVCC, 2 SECC allowed; `Pricing` 0/1/2. The EV picks the first parameter set with its connector, ControlMode 2, MobilityNeedsMode 1.
- **Vector tooling**: `xtask vectors` skips vectors newer than their XML and retries the Java run, because Xerces fetches a DTD from w3.org while loading the xmldsig schema and w3.org rate-limits.
- **DC grammar** (verified with EXIficient): the DC document root has 49 elements (6-bit code; CPDReq = 15, CPDRes = 16, CableCheck 11/12, ChargeLoop 13/14, PreCharge 17/18, WeldingDetection 19/20). The energy transfer mode is a substitution group coded in 2 bits (BPT = 0, plain DC = 1). `TargetSOC` (0..=100) is a 7-bit offset. Optional trailing elements sit in a 2-bit state. In -20 the flow order is ServiceSelection, `DC_ChargeParameterDiscovery`, then `ScheduleExchange`.

## The generator (`exi-gen`)

- **Pipeline**: `xsd.rs` reads the XSD subset the schemas use and errors on anything else; `model.rs` resolves types to EXI datatypes and flattens each complex type into a list of *slots* (attributes first, sorted by name, then the particles; extension = base first); `emit.rs` writes Rust; `dump.rs` prints the grammar for diffing with EXIficient (`xtask/java/DumpTree.java`, structurally identical states merged). `cargo xtask gen` regenerates when a schema or the xtask binary is newer than the output; `cargo xtask grammars` runs the diff.
- **Layout instead of tables** (`exi::layout`): a type's grammar is its slots (`min`, `max`, number of alternatives); the productions of a state are computed on demand (current slot while more copies are allowed, following slots up to the first mandatory one, then EE if everything left is optional), so `maxOccurs=2048` costs nothing. Event code = index, width = `ceil(log2(n + 1))`; the document root has `ceil(log2(global elements + 1))` bits (the `SE(*)` code is the extra one).
- **Facts the grammar diff confirmed**: attributes come before elements and are sorted; substitution groups (head included, even when abstract) and choices list their alternatives in order, the group sorted by local name; a choice and a substitution group are the same thing to the layout; integers with a range of at most 4096 values are n-bit offsets (this includes `xs:byte`, `xs:unsignedByte`, percent), wider unsigned ones are EXI unsigned integers, wider signed ones EXI integers.
- **Generated API**: one struct per complex type (`Copy`, borrowing from the arena via `&'a [T]` / `&'a str`; a lifetime only where needed), one enum per choice or substitution group (`...Choice`; identical choices share one), `#[repr(u8)]` enums for enumerations (`from_index`, `xml_name`), `Message` + `decode(buf, arena)` per module, `Msg::encode(&self, out)` for every request/response. Names are derived by `names.rs` (word splitting: `EVMaximumChargePower` -> `ev_maximum_charge_power`, `PnC` stays `PnC`). Elements typed from xmldsig (`Signature`, `X509IssuerSerial`) are omitted: decoding them is `Unsupported`; a type that *requires* one (`CertificateInstallationReq` and friends) is not generated at all.
- **Decoding lists**: a dry run over a copy of the stream counts the entries, then the arena slice is allocated at exactly that size. Nested lists make this O(depth x size); the string table is cloned for the dry run (capacity 64 distinct strings per message).
- **Stack use**: the generated messages are small (`size_of` of the largest, `ScheduleExchangeRes`, is 224 bytes; `tests/sizes.rs` keeps them under 2 KiB) because lists live in the arena.
- **Fuzzing**: `tests/vectors.rs` flips bits in valid streams and requires that decoding returns. A real fuzz target (cargo-fuzz) is still to do.
- **Open**: choice enum names such as `AReqAuthorizationModeChoice` are mechanical (override table if they bother anyone); the wrapper types (`ServiceList { service: &[..] }`) are not flattened; AC, ACDP and WPT are not generated yet (add them to `ISO20.files/modules` and decide the module names).

## Compliance review against ISO 15118-20:2022 (2026-10-15)

The standard text is in `standards/`. Reading the EVCC requirements of clause 8.5/8.6 and 7.7 against what is built shows the happy path is right but several mandatory behaviours are missing or wrong. Ordered by priority.

**Fixed (all six, with tests):**

1. `DC_WeldingDetection` (V2G20-1448, 1573, 1461, 1462): after `PowerDeliveryRes(Stop)` the session asks the host to open the contactors (`Notice::OpenContactors` / `Event::ContactorsOpened`), sends `DC_WeldingDetectionReq(Ongoing)` repeatedly while the voltage at the EV's inlet is still above 20 V, then `Finished`, then `SessionStopReq`. The generic 60 s `Ongoing` bound applies (the standard defines no welding timer).
2. Invalid messages are ignored (V2G20-440): wrong message, wrong payload type or undecodable payload only logs `Record::Ignored`/`DecodeFailed`; the response timer keeps running. Still fatal: bad V2GTP framing, our own arena being full, and valid responses whose content we cannot use.
3. `Timer::Setup`: 20 s from `Start` until `SessionSetupRes` (V2G20-2298, 448).
4. `Config::allow_unsecured` (default false): without TLS the session ends with `EndReason::TlsRequired` instead of offering -20 (V2G20-1235, 1237).
5. `WARNING_PowerToleranceNotConfirmed` is tolerated on `PowerDeliveryRes(Start)` (V2G20-1438). Other WARNING codes still end the session, which the standard allows where it defines no remedy (e.g. V2G20-1583 for `AuthorizationRes`); implement the remedies when PnC arrives.
6. `Timer::Sequence` (`sequence_performance_ms`, 40 s): bounds the host actions closing contactors, ramp-down and opening contactors. The charge loop interval (default 100 ms) stays below the 0.25 s of Table 217. `Timers` now holds three commands per step.

**Decided, not yet built:** `SessionStopReq` on error exits (V2G20-2644 for non-critical stops before `Start`), standby/pause, service renegotiation (V2G20-1476), `MeteringConfirmation` on side stream `0x8102` when the EVSE asks (V2G20-1621), resumed sessions (V2G20-2098), the other `EVSENotification` values.

**TLS (slice 5) is bigger than planned** (7.7): TLS 1.3 with *mutual* authentication must be supported (V2G20-1264) so the EVCC needs a client certificate chain; cipher suites `TLS_AES_256_GCM_SHA384` then `TLS_CHACHA20_POLY1305_SHA256` (Table 6, V2G20-1858); named groups `secp521r1` / `x448` in the order of Table 7. EVSE and EVCC test certificates are needed in the loopback and `unshare` tests.

**Verification gaps:** the grammar of every message equals EXIficient's, but value-level vectors exist only for the messages the session uses; the PnC types, BPT and the scheduled-mode types are generated but untested. 

**TLS library decision (2026-10-15).** rustls cannot do this standard: no provider implements `secp521r1`/`x448` key exchange or Ed448, and it has no CBC or static-ECDH suites that ISO 15118-2 needs (Table 7: `TLS_ECDH_ECDSA_WITH_AES_128_CBC_SHA256`, `TLS_ECDHE_ECDSA_WITH_AES_128_CBC_SHA256`; -20 requires them after the TLS 1.3 suites for -2 compatibility, V2G20-2056..2066). Other Rust stacks (boring, wolfssl crate, mbedtls crate, embedded-tls, graviola, RustCrypto) lack groups or TLS 1.3. Decision: the `openssl` crate in `evcc-linux`. Probed with `s_server`/`s_client` on OpenSSL 3.6.4 and 4.0.3: TLS 1.3 mutual auth with P-521 certs, x448 and secp521r1 groups, Ed448 certs, both Table 6 suites, and TLS 1.2 `ECDHE-ECDSA-AES128-SHA256` all work. `ECDH-ECDSA-AES128-SHA256` (static ECDH) is not available in either, so an SECC claiming -2 conformance (V2G2-602) needs another library or an older OpenSSL; the EVCC needs only one suite (V2G2-603).

**TLS slice done.** `evcc-linux::tls` builds client and server `SslContext`s from PEM credentials: TLS 1.3 only, Table 6 suites, groups `secp521r1:x448`, sigalgs `ecdsa_secp521r1_sha512:ed448`, mutual authentication, chain checked against the trust anchors but no host name check. `run` is generic over `Transport` (`TcpStream` or `SslStream<TcpStream>`); the timers still work as socket read timeouts. `evse_sim::serve` serves any stream. `tests/tls.rs` generates P-521 and Ed448 PKIs and runs a full DC session over TLS, and checks that unknown CAs (either direction) and P-256 certificates are refused. **Codec performance pass** (`cargo bench -p iso15118-20`, plain `std::time` over the 50 reference vectors; Apple M-series, release): decode 22.1 to 12.5 µs (69 to 122 MB/s), encode 16.1 to 7.4 µs (95 to 207 MB/s) for the 1531 bytes of the vectors. What mattered, in order of gain (a `sample` profile guided each step):
- the per-message string table: 64 entries were initialized for every message and copied for every list (a quarter of the time). It is now left uninitialized (`MaybeUninit`, via `uninit().assume_init()` because the repeat expression `[MaybeUninit::uninit(); N]` compiles to a memset), only the used part is cloned, and the caller owns it (`Enc::new(out, &mut table)`, `Dec::new(buf, arena, &mut table)`) so it is never moved;
- `#[inline]` on the small `Enc`/`Dec`/bit I/O methods: they sit in another crate than the generated code and were real calls with their `Result` returned through memory;
- word-wide bit I/O (64-bit accumulator in the writer, an 8-octet load in the reader) instead of one bit per step, byte-aligned memcpy for binary values;
- event codes by arithmetic instead of enumerating productions through closures: per-slot tables (`Slot::new` + `table`/`fill`, computed at compile time: prefix sums of the alternatives, end of the optional run) make `Layout::{width, write_start, write_end, read}` O(1) apart from the scan inside a run; `for_each` stays as the reference (used by `exi-gen dump`), and a test checks both against each other in every state of several layouts;
- ASCII strings in one pass (the arena rolls back for the rare non-ASCII string), `CH`+value+`EE` of fixed-width values in one write (`elem_bits`).
Left on the table: what a profile still shows is `Layout::read` (about 9 ns per event) and moving decoded structs through `Result<Self, DecodeError>` (`DecodeError` is 24 bytes, so every `Result` goes through memory; a thin payload would put it in registers), plus straight-line generated code for plain sequences of mandatory elements. Code size was not measured.

**Service renegotiation (plan step 4, 2026-10-16).** `ServiceRenegotiationSupported` is read from the first `ServiceDiscoveryRes` only (V2G20-1480). **Schedule renegotiation (plan step 4, 2026-10-16).** A side stream on V2GTP payload type `0x8101` next to the charge loop (8.6.5.1, Annex F): `DC_ChargeParameterDiscoveryReq`, `ScheduleExchangeReq` (repeated while `Ongoing`, bounded by the Ongoing timeout, pause = the poll interval but at least 50 ms), `PowerDeliveryReq` with ChargeProgress ScheduleRenegotiation and a new profile; the `PowerDeliveryRes` OK ends it (`Notice::ScheduleRenegotiated`). **Session pause and resume (plan step 4, 2026-10-16).** Pause: after the usual orderly stop (`PowerDeliveryReq(Stop)`, contactors, welding detection) the vehicle sends `SessionStopReq(Pause)` (V2G20-1540) and the session ends with `EndReason::Paused(Resume)`, which carries the session id, the selected service and the charger's `ServiceRenegotiationSupported`; closing the TLS connection is the host's (V2G20-2071, the `evcc-sim` process simply drops it). **Message signatures (plan step 4, 2026-10-16).** Three layers.
- *Codec.* The header's `ds:Signature` (profile of V2G20-771: `SignedInfo` with one canonicalization method, one signature method and references each with at most one transform, and the `SignatureValue`; no `KeyInfo`, `Object`, `HMACOutputLength`, reference `Type`, wildcards) is the hand-written `iso15118_20::signature` (`exi-gen` has `AltTy::External` for such types; xmldsig has wildcards and mixed content that the generator does not model). `exi::layout::Layout` got a second field, `tail`: productions after `EE` that are only counted (the generic character events of mixed content, in every state where the element can end). `MessageHeader<'a>` carries `signature: Option<Signature<'a>>`, so every message type has a lifetime now (`MessageHeader::new(id, stamp)` for the unsigned header; `Notice::ChargeParametersDiscovered` carries the limits, not the message). Checked byte for byte against EXIficient: one reference with transform, two references with ids on the signature, signed info and value, the algorithm strings coming from the string table the second time. The grammar diff keeps xmldsig opaque on both sides (the unmodelled part is recursive).
- *Fragments.* What is hashed and signed is the schema-informed EXI *fragment* (V2G20-1449): `[header octet] SE(code, 9 bits) content ED(code)`, the start event chosen among all 281 element declarations of CommonMessages, CommonTypes and xmldsig (global and local, unique qualified names, sorted by local name then namespace; `exi-gen`'s `fragment` module computes the table and writes `generated/fragment.rs` with the codes of the elements that carry an `Id`, `ELEMENTS`, `END`, `CODE_BITS` and `SIGNED_INFO`). `signature::encode_fragment(out, code, |e| value.encode_content(e))`. Verified against EXIficient in fragment mode (`cargo xtask vectors` has a third manifest column `fragment`): the OEM provisioning certificate chain and a `SignedInfo`.
- *Crypto (`evcc-linux::xmlsig`, OpenSSL).* `sign(key, &[(uri, fragment)])` digests the fragments, builds the `SignedInfo`, encodes it as a fragment and signs it; `verify(public key, signature, fragments)` checks algorithms against the key, every reference against its fragment (each fragment referenced exactly once) and the value. Suites by key: ECDSA secp521r1 + SHA-512 (value r || s, 132 octets) and Ed448 + SHAKE256 (digest of 64 octets, value 114). Tests: round trips through the codec in a header, tampered fragment, value, wrong key, wrong suite, several references.
Assumptions to check against another implementation: the digest and the signature cover the fragment stream *with* its EXI header octet (the standard does not say; EXIficient-based stacks do it that way); the SHAKE256 digest length (not given by the standard); the ECDSA value as r || s (xmldsig-more). Not done: the session machine does not sign anything yet (PnC: AuthorizationReq's `PnC_AReqAuthorizationMode`, `CertificateInstallation`, metering confirmation, price schedules; the fragment codes are there), and the signed element's `Id` must be unique in the message (the caller chooses it).

**SLAC validation by control pilot toggling (2026-10-16, ISO 15118-3 9.4, A.9.3).** `slac::Config::validation` {Never, Ambiguous, Always} (default Never, so the policy `accept_potential` behaves as before), `toggles` (1 to 3, 0: per run) and `toggle_state_ms` (300). A chosen charger that needs validation gets the step 1 `CM_VALIDATE.REQ` (unicast, timer 0, retried with `TT_match_response` and `C_EV_match_retry`, V2G3-A09-62); "ready" leads to step 2 (broadcast, the listening time in units of 100 ms covering the 2n+1 states of Figure 12 plus one unit, at most 35), `Step::toggle` tells the host to make the B-C-B sequence while the machine's timer for the window runs, then the answer is awaited (A09-70, 71). Only `Success` with the number of toggles made matches the charger (A09-73) and the `CM_SLAC_MATCH.REQ` follows (A09-74); everything else drops the candidate and the next one is tried (A09-63, 65, 72), the run fails with `Failure::ValidationFailed` when none is left. "Not ready" is asked again within the retries, "not required" is followed for a charger that is surely the one and overruled for an ambiguous one, "failure" (no such feature) is no reason to refuse a sure charger or, with `accept_potential`, an ambiguous one (A09-51). `homeplug` has `ValidateReq`/`ValidateCnf` (signal type, timer or toggle number, result; no application and security type prefix as in the other SLAC messages); the MMTYPEs 0x6044/0x6045 are those of the open HomePlug implementations since the standards texts leave them to the HomePlug spec, so they are unchecked. Nine tests in virtual time against the simulator and two scenarios (`slac-validation`, and without the pilot connection: zero toggles counted, `ValidationFailed`). Not done: a real control pilot (the host trait is the place), `TP_EV_vald_toggle` below 600 ms is not rejected, the charger side (validate only the EV that started matching, one validation at a time with "not ready" for others, V2G3-A09-78) is minimal in the simulator.

**Certificate profile checks and OCSP (2026-10-16, ISO 15118-20 Annex B, 7.7.3).** `evcc_linux::certificates::check_chain(chain, Peer::{Secc, Vehicle}, now)` checks a chain (leaf to root, DER) against the profile of each position: version 3, positive serial, ecdsa-with-SHA512 / Ed448 as in the signed part and outside with no parameters, the key (secp521r1 uncompressed point or Ed448), name attributes (only C, O, OU, CN, DC, once each, O and CN mandatory, the SECC certificate needs C), validity now and issued within the issuer's validity (V2G20-1004), every extension against the table (those not defined are refused, V2G20-2686, criticality where the table fixes it: key usage, basic constraints, extended key usage, authority information access and CRL distribution points are critical, certificate policies not), key usage bits, basic constraints (CA, path length 1 for sub-CA1 and 0 for sub-CA2, V2G20-911: one sub-CA is a sub-CA2), extended key purposes (serverAuth for a SECC, clientAuth and optionally serverAuth for a vehicle), AuthorityInfoAccess with id-ad-ocsp and a URI, key identifiers by RFC 5280 method 2 (V2G20-1851, 1852), the signatures along the chain, at most three certificates below the root (V2G20-1003), vehicle certificates with CRL or OCSP information (V2G20-2599), and the identifier in the common name of the leaf (Annex C: SECCID, EVCCID with the check digit of C.6; the EMAID and EVCCID examples of the standard come out as printed, the SECCID example of C.3.2 does not: the same algorithm gives 4, not 2). `tls::check_peer_certificates(stream, peer, policy, report)` applies it after the handshake (`CertificateChecks` Off, Warn, Enforce). OCSP: `evcc_linux::ocsp::check_revocation` takes the stapled and other responses and checks successful status, signature and responder chain (V2G20-2413, 2414), status good (2415), nextUpdate present, within one week (1021), not expired, and a status for the leaf, or with `require_all` for every certificate below the root (2416); `tls::connect` sends `status_request` (V2G20-2388), `Credentials::ocsp_response` makes a server staple one, `tls::check_peer_ocsp` checks it. **Limits and findings:** (1) OpenSSL gives a TLS client one stapled response, the leaf's; the per-certificate responses of a TLS 1.3 handshake for the sub-CAs cannot be delivered or sent through its API, so `require_all` fails for any chain with a sub-CA unless the host brings more responses (cached, or asked of the responder, V2G20-2411); the simulators default to the leaf only. (2) The profiles make AuthorityInfoAccess and CRLDistributionPoints critical; OpenSSL reports that as an unhandled critical extension, so the TLS contexts let those two through (nothing else), and the OCSP store ignores critical extensions, relying on the profile check. (3) Ed448 SECC certificates need keyAgreement set (Table B.6 says 1), which an Ed448 key cannot do; implemented as written. (4) The vehicle tables make AuthorityKeyIdentifier and SubjectKeyIdentifier critical (RFC 5280 says not); either is accepted. (5) The subject of a SECC or vehicle certificate "shall not contain any further values" (V2G20-2584, 2598) but the tables allow C, OU and DC; the tables are followed, and a domain component must be CSO or EV. Not covered: cross certificates (V2G20-1002, 1005, 1853), the other services' profiles (provisioning, e-mobility, OEM provisioning, private environment, OCSP signer), GeneralizedTime encoding of times, the 25 years of a root, CRLs, the vehicle's OCSP responses obtained by the SECC. Test PKI: `scenarios::profile_pki` makes conformant chains (V2G root, sub-CA1, sub-CA2, leaf, on P-521 and Ed448, for a SECC or a vehicle) with one flaw on request and OCSP responses (good, revoked, too long, expired, stranger, other certificate); the P-521 and Ed448 PKIs of the runner follow the profiles now, the P-256 one stays plain. Simulators: `evcc_sim::Tls::{certificate_checks, ocsp_checks, ocsp_require_all}`, `evse_sim::Settings::certificate_checks` and `--ocsp FILE`; `dc-tls-ed448` and `dc-tls-slac` enforce both, `dc-tls-profile-violation` has the vehicle refuse a P-256 chain. A connection that fails the handshake or the checks ends one session of `evse-sim`, not the process.

**Audit of the simulators' values against ISO 15118-20 (2026-10-17).** Both simulators now test the state machines against each other, so what they put into messages was checked against the text (Annex A and C, 8.3.4.3, 8.3.4.5, 8.3.5, 8.6). **Found and fixed:**
- *Charger header `TimeStamp` in seconds* (V2G20-1534: microseconds in SECC time, V2G20-1537: larger with every message). The charger sent whole seconds, which equal stamps within one second broke, and the vehicle learned a wrong clock offset from it, so its own stamps were wrong too. Now microseconds, strictly increasing.
- *`FAILED_WrongChargeParameter` outside the charge parameter discovery* (Table 226): the charger answered a non-Dynamic charge loop and schedule exchange with it; now `FAILED`. The response code applicability of Tables 224 and 226 is now `iso15118_20::ResponseMessage::allows`; the vehicle logs `Record::ResponseCodeNotAllowed` for a response outside it, the charger notes `violation:` for what it sends (also the knob codes, which stay free on purpose), and the page offers the codes defined for a message first.
- *Responses of the wrong type*: an unknown session id was always answered with an `AuthorizationRes`; now with the response of the request's type (V2G20-460), and a request out of sequence gets `FAILED_SequenceError` of its type (V2G20-459) instead of a silent close.
- *`OK_CertificateExpiresSoon` and `OK_PowerToleranceConfirmed` did not count as OK* in the charger, so an expiring contract would not have advanced the session.
- *EVCCID* `WMIV1234567890ABCDEX` had the letter I (V2G20-2090, 2128: no I, O, Q), no valid check digit; now the example of C.5.2. The identifier checks reject I, O, Q.
- *Charge loop limits against the discovery* (V2G20-2198, 2199 for the vehicle, 2654, 2655 for the charger): the vehicle holds its charge loop limits within those it announced (`Config::enforce_cpd_limits`, default on; off to test a charger), the charger notes a vehicle that does not (`fail_on_limit_violation` answers `FAILED`), the vehicle logs `Record::Violation` for a charger that does not. Live limit editing can no longer make a compliant vehicle break the rule by raising a maximum.
- *`DC_PreChargeReq.EVPresentVoltage`* was the battery voltage; V2G20-2180 puts the voltage at the inlet, which follows the charger's output until the contactors close; now the last inlet measurement (zero before the first).
- *`EVPowerProfile` in Dynamic control mode* (8.3.4.3.8.2): was the vehicle's maximum power until departure; now the fastest charging to `EVMaximumEnergyRequest` at the lower of the vehicle's and the charger's announced maximum power.
- *Energy requests of the simulated car* were constants (40 / 60 / 0 kWh); with the battery model they follow the state of charge (what the target and minimum SOC need, what fits before full).
- *`EVSEPowerRampLimitation`* is in percent per minute (Table 172), not watts per second: `power_ramp_limitation_percent_per_min`.
- *Limit achieved flags* were always false; now set when the current, power or voltage limit is what limits the delivery. A modelled current below the charger's minimum current is zero (Table 172: "can deliver with the expected accuracy").
**Looked at and fine:** the parameter names and integer types of the service parameter sets (Table 207), `NotificationMaxDelay` for Pause (60 s, V2G20-1850), `DepartureTime` greater than zero and relative to the message time stamp (V2G20-2103, 2104), `MaximumSupportingPoints` 12 (V2G20-1202), the DC ranges (400 V battery, 200 to 450 V, 150 to 920 V), welding detection below 60 V, pre-charge tolerance 20 V, the identifiers' check digits. **Known and left:** no CV taper (the vehicle's maximum current does not fall at high state of charge), the charger echoes the vehicle's voltage instead of modelling a cable drop (V2G20-2185 note 2), `GoToPause` (V2G20-2121, 2122) and a zero first schedule entry are not handled by the vehicle, the `EVPowerProfile` has one entry, `DisplayParameters` carries only the present SOC (the rest is mandatory for `MobilityNeedsMode` 2, which the simulators do not use), the charger never updates `DepartureTime`, `TargetSOC` or `MinimumSOC` (V2G20-1291), the column of Tables 224 and 226 for each code was read from the text extraction of the PDF and by meaning, the EVSEID format (IEC 63119-2) is not checked.

**ISO 15118-2 (2026-10-17): DC, AC, Plug & Charge.** Schemas from the same ecog-io repository (`data/schemas/iso15118-2`, fetched by `cargo xtask setup`).
- *Codec.* `exi-gen` group `iso15118-2`, crate `crates/codec/iso15118-2`. New in the generator: simple types declared inside an element, `simpleContent` (a text slot coded like a mandatory attribute: `eMAID`, `DHpublickey`), facets that do not change the encoding (`minLength`, `pattern`). **`valuePartitionCapacity` is 0 here too** (Table 11), as in DIN: found by the Python partner failing on a repeated string (EXIficient `lvs is null`) and then read in the text. 52 EXIficient vectors (`iso2_*`: all messages of the DC and AC flows, certificate installation and update, a signed header); `PhysicalValue` has a mandatory unit (DIN's is optional).
- *Signatures.* Two grammars (J.2, J.4): the signed *elements* (`AuthorizationReq`, ...) are fragments over the `V2G_CI_MsgDef` schema's declarations (`fragment::AUTHORIZATION_REQ`, ...), the `SignedInfo` is a fragment over the xmldsig schema alone (`fragment::XMLDSIG_SIGNED_INFO`). Both match EXIficient byte for byte, and the Python library accepted our digest and, after this fix, the signature. **This was a bug in -20 as well**: V2G20-1449 says the signature header uses the xmldsig schema as entry point, and `SignedInfo::encode_fragment` used the CommonMessages-wide table; fixed, vector regenerated. The -20 signatures are still only checked against EXIficient and ourselves (the Python library has no -20 PnC).
- *Vehicle (`evcc_core::iso2`).* `Config::ISO2_DC` / `Config::ac(three_phase)`, `Mode`. Flow: SAP (`urn:iso:15118:2:2013:MsgDef` 2.0), SessionSetup, ServiceDiscovery, PaymentServiceSelection, (PaymentDetails), Authorization (repeated while `Ongoing`/`Ongoing_WaitingForCustomerInteraction`), ChargeParameterDiscovery (DC or AC parameters, `MaxEntriesSAScheduleTuple`), then DC as in DIN (control pilot C, cable check, pre-charge, power delivery with profile and `SAScheduleTupleID`, current demand, stop, welding detection) or AC (power delivery at once, the ChargingStatus loop, stop). `Ev::ac_limits`, `Contract::emaid`. The energy transfer mode follows the inlet: `Core` DC_core, `Extended` DC_extended, `Dual2/4` DC_combo_core.
- *Plug & Charge, both standards.* The `Contract` trait and `evcc_linux::xmlsig` serve both: a new suite `EcdsaP256` (secp256r1, SHA-256, `r||s` of 64 octets; for -2 contracts) next to P-521 and Ed448 (-20), and `PemContract` takes the eMAID from the certificate's common name without separators. Vehicle: `PaymentDetailsReq` (eMAID, chain), the challenge from its answer, `AuthorizationReq` with `Id` and the challenge, signed in the header. Charger (`evse-sim`): chain against the eMSP root (`pnc::check_contract_chain`, shared with -20), the challenge, the signature (`pnc::verify_iso2`), `FAILED_CertChainError`, `FAILED_CertificateExpired`, `FAILED_ChallengeInvalid`, `FAILED_SignatureError`.
- *Charger.* `Config::protocols` has `iso15118-2`; `Config::iso2` (modes, EVSE id, contract payment, `Ongoing` answers, shutdown after n rounds, AC voltage and current). Scenario runner: the partner's `protocols` and `auth_modes`; for a partner over TLS the vehicle uses the partner's own contract (leaf, sub-CA 2, sub-CA 1); `profile_pki` makes P-256 chains for -2 contracts.
- *Evidence.* In memory (`iso2_flow.rs`, 8), own-charger scenarios `dc-iso2`, `ac3-iso2`, `dc-iso2-pnc`, `ac3-iso2-pnc`, and against the Python SECC: `iso15118-python-iso2-ac3`, `-iso2-dc`, `-iso2-pnc` (TLS 1.2, its test PKI, its eMSP root).
- *Not done / to know.* No metering receipt (signed `MeteringReceiptReq`; the charger never asks for one), no `ServiceDetail` or value-added services, no certificate installation/update (the messages are in the codec), no `Pause`/renegotiation (`ChargeProgress::Renegotiate`, `SessionStopReq` Pause), no sales tariffs in the vehicle, the web page has no -2 choice yet, and the charger side of -2 is tested only against our own vehicle. BPT in -20: see the entry below.

## SLAC modem: QCA7000 family (2026-10-17)

Done: `homeplug::modem` (CM_SET_KEY.REQ/.CNF, the vendor version request/answer, `network_id`), `evcc_linux::slac::QcaModem` (a `Modem` for a QCA7000/QCA7005/QCA7020 behind a network interface, e.g. the `qcaspi` driver's; the local device address `00:B0:52:00:00:01`), `PacketSocket::open_any` (an interface that is a bridge port: a socket bound to the HomePlug protocol never sees frames addressed to the host there, found on the board), the `tls` feature of `evcc-linux` (default; without it the crate builds without OpenSSL, which is what cross-compiling for a small board needs), the example `plc_probe`, the setting `qca_modem` of `evcc-sim`. Tests: the frames against captures from the board, the driver against a fake modem on a veth cable (`scenarios/tests/modem.rs`).

Checked on a Heliox EVAChargeSE board (QCA7005, firmware MAC-QCA7005-3.3.0.31-00-20231004-CS, `qcaspi`, the interface bridged): `plc_probe eth1`, cross-compiled for `armv5te-unknown-linux-musleabi`, reads the version from the modem. Also checked on the board (with the owner's go-ahead; the modem was reset afterwards, which restores the key of its PIB): `plc_probe eth1 --set-key` sends `CM_SET_KEY`; the modem answers `Result` 1 for a key it takes and 0 for an invalid key type, and its network then has the network ID that `homeplug::modem::network_id` computes (so the NID derivation, including the shift of the last octet, is right). Found on the way: **a version 1 MME needs the two octets of fragmentation information (FMI) after the MMTYPE** - the modem ignored `CM_SET_KEY` without them. The SLAC messages shared the header and had no FMI, so they gain it too (`HEADER_LEN` 19): confirmed with Qualcomm's own `pev` emulator (open-plc-utils, on the board, with `eth1` taken out of its bridge for the run; restored after): its `CM_SLAC_PARAM.REQ` has the FMI before the application type, and our frame is byte for byte the same (test `parm_req_is_the_frame_of_the_qualcomm_reference_emulator`); its `CM_SET_KEY.REQ` is ours but for the nonce, its network id for its default key equals what `network_id` computes, and it takes result 1 as success. Not checked on hardware: a link between two modems; the link check after the key is a settle time (the modem's network info message was not decoded).

The board is an EVSE side modem (PIB `hlx-secc`); a real SLAC run needs a second PLC node for the vehicle side.

## ISO 15118-20 Plug & Charge checked against the Python SECC (2026-10-17)

The Python library does verify -20 Plug & Charge (signature over the `PnC_AReqAuthorizationMode` fragment, challenge), which this plan had wrong. `interop/iso15118-python-pnc` (TLS 1.3, the library's test contract, secp256r1 with SHA-256) passes: the library decodes our `AuthorizationReq` with its signature header, finds the digest and the signature right, and accepts the challenge.

Found on the way, and fixed: **ISO 15118-20 needs `valuePartitionCapacity` 0 as well.** The library's codec sets `valueMaxLength` and `valuePartitionCapacity` to 0 for every protocol it speaks; our -20 encoder used string table hits, which its decoder cannot follow (`NullPointerException ... "lvs" is null`). Only messages with a repeated string show it, such as the signature header (algorithm URIs) of a Plug & Charge authorization, a `ServiceDetailRes` with several parameter sets or a `SupportedAppProtocolReq` with several entries, so nothing else caught it. `exi-gen` now emits `Table::without_values` for the -20 and handshake groups, `EncodeVector` sets the capacity for every schema, and the vectors were regenerated (note `cargo xtask vectors` writes only missing files: delete `data/vectors/*.hex` to regenerate). A 20-entry handshake request is larger now (the namespace repeats in full).

What this does not check: the library supports only the secp256r1/SHA-256 suite (its digest and ECDSA are fixed), so the suites -20 prescribes (secp521r1 with SHA-512, Ed448 with SHAKE256) have no independent verifier here; they use the same structure with other primitives. The contract chain is not verified by the library in this path either.

## ISO 15118-20 AC (2026-10-17)

- **Codec:** `V2G_CI_AC.xsd` is the module `ac` of the -20 group. Substitution groups are now taken per entry schema (`exi-gen` `Model::entry`): the control-mode groups of `CommonTypes` have the AC members in the AC module and the DC ones in the DC module, as EXIficient does with one schema. 15 vectors (`ac_*`) match byte for byte in both directions: base and BPT discovery, Dynamic and Scheduled loop modes (BPT too), one and three lines.

## SLAC modem link check (2026-10-17)

`VS_NW_INFO` (0xA038/0xA039, MMV 1 with FMI, OUI, zeros) is decoded (`homeplug::modem::{nw_info_req, parse_nw_info_cnf, NwInfo::joined}`) and `QcaModem::link_up` asks the modem: up when its first network has the key's network id and a coordinator other than the modem itself; a modem that does not answer gets the old settle time. **Checked on the QCA7005:** the request frame is `plctool -m`'s; the answer was captured with the pev default key, with another key (the network id changed to the one `network_id` gives) and after restoring it: five header octets, the number of networks, then network id, short id (changed with every network formed: 0e, 02, 03), TEI 1, role 2 and the coordinator = the modem's own address, TEI 1, no stations: a lone modem reads as "alone". `plc_probe` prints it. **Not checked:** the answer of a modem that has joined someone else's network (needs a second modem; the fake-modem test builds that frame from the layout above), and several networks or stations (only the first network is read). `plctool` cannot show the answer on the board (the interface is a bridge port); capture with `tcpdump -XX ether proto 0x88e1`.
